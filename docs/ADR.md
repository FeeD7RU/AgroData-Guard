# Краткие архитектурные решения

## 001 — Модульный монолит

Для двух студентов быстрее и надёжнее один Python-процесс с явными модулями.
HTTP, CSV и MQTT преобразуются в одну схему, а не получают отдельную бизнес-логику.
Выделять worker стоит после измерения нагрузки, не заранее.

## 002 — Неизменяемое сырьё и отдельные решения

Raw отражает то, что сообщил источник. Suggested и accepted относятся к анализу.
Review хранится append-only. Это делает сравнение методов и аудит возможными даже
после неверной коррекции. На SQLite immutability защищена также DB triggers.

## 003 — Каузальная online correction

Interpolation требует будущего соседа, которого нет при streaming ingestion.
Поэтому live использует median, а offline interpolation имеет отдельный режим и
маркировку в benchmark. Длинные пропуски вызывают abstention, не экстраполяцию с
выдуманной высокой уверенностью.

## 004 — Прозрачный baseline и два score

Нет выбранной «лучшей ML-модели». Стартовый live pipeline сочетает физические и
простые временные правила. Isolation Forest доступен для сравнения и подключения.
Anomaly score описывает силу сигнала нарушения, correction score — пригодность
контекста восстановления. Ни один из них не является откалиброванной вероятностью.

## 005 — MQTT ACK после durable spool

Первоначальный вариант с ACK только после HTTP создаёт backpressure на broker
callback и усложняет reconnect. Gateway сначала fsync-ит сообщение, затем ACK;
отдельный поток доставляет HTTP с тем же measurement_id. Это at-least-once delivery,
а не распределённая транзакция. Invalid payloads переходят в quarantine.

## 006 — Собственный frontend без отдельного build

В MVP dashboard состоит из HTML/CSS/JavaScript с SVG-графиками и polling.
Так одна команда запускает API и UI, без CDN и второго toolchain. Никаких встроенных
измерений: все таблицы и графики приходят из API. При развитии frontend можно заменить,
сохранив REST-контракт.
